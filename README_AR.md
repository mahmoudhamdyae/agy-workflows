## 🔍 الشرح التفصيلي للمسارات بحسب الفئات

### الفئة الأولى (A): إدارة الإصدارات والتحكم في الكود (Git & Version Control)

#### 01. الالتزام في Git — Git Commit
* **الأمر السريع**: `/commit`
* **كلمات التحفيز البديلة**: *"commit my changes"*, *"make a commit"*, *"احفظ التغييرات في جيت"*
* **متى يُستخدم**: عند الانتهاء من جزء عمل محلي وتود حفظ التعديلات في مستودع Git المحلي.
* **الآلية الذكية**:
  1. التحقق من وجود مستودع Git وسلامته وعدم وجود عمليات دمج أو rebase معلقة.
  2. فحص شامل لمنع إدراج الملفات السرية أو الحساسة (مثل `.env` و `.pem` و `id_rsa`).
  3. تجهيز التعديلات الآمنة فقط (Selective Staging) وتجنب استخدام `git add .` الأعمى.
  4. تحليل الفارق المجهز (Staged Diff) وصياغة رسالة التزام احترافية بصيغة **Conventional Commits** (مثل `feat:`, `fix:`, `refactor:`, `chore:`).
* **صمامات الأمان**: **يحفظ التعديلات محلياً فقط ولا يقوم إطلاقاً بالرفع (Push) إلى الخادم البعيد.**

#### 02. الالتزام والرفع إلى المستودع — Git Commit & Push
* **الأمر السريع**: `/commit-push`
* **كلمات التحفيز البديلة**: *"commit and push"*, *"commit-push"*, *"commit and sync"*, *"احفظ وارفع التعديلات"*
* **متى يُستخدم**: عندما ترغب في حفظ التغييرات المحلية ومزامنتها مع الخادم البعيد (Remote) في خطوة آمنة واحدة.
* **الآلية الذكية**:
  1. تنفيذ كافة فحوصات الأمان والتجهيز الانتقائي الخاصة بمسار `/commit`.
  2. التحقق من وجود Remote ومسار التتبع للفرع الحالي (Upstream Tracking).
  3. تنفيذ `git fetch` للتأكد من عدم وجود تعديلات أحدث على الخادم البعيد لم يتم سحبها محلياً.
  4. رفع التغييرات بسلاسة وأمان.
* **صمامات الأمان**:
  - يتوقف فوراً إذا وجد تعديلات جديدة على الخادم البعيد ويطلب منك سحبها أولاً (`git pull / rebase`).
  - **يمنع منعاً باتاً استخدام الرفع القسري** (`--force`, `-f`, `--force-with-lease`).

### الفئة الثانية (B): تحليل المشاريع وصيانتها (Project Analysis & Maintenance)

#### 03. التعرف على المشروع — Project Onboarding
* **الأمر السريع**: `/project-onboarding`
* **كلمات التحفيز البديلة**: *"onboard this project"*, *"explain this codebase"*, *"اشرح لي هذا المشروع"*
* **متى يُستخدم**: عند فتح مشروع جديد لأول مرة، أو الانتقال بين المشاريع، أو انضمام مبرمج جديد للفريق.
* **الآلية الذكية**:
  1. تشغيل أداة التعرف التلقائي `project_detector.py` لقراءة ملفات التكوين (`pubspec.yaml`, `package.json`, `composer.json`, إلخ).
  2. قراءة ملفات التوثيق والإرشادات الحالية (`README.md`, `AGENTS.md`).
  3. تحديد نقاط الانطلاق (Entry Points مثل `main.dart`, `app/layout.tsx`, `index.ts`).
  4. رسم خارطة لمعمارية إدارة الحالة (State Management)، واجهات الاتصال (API Services)، وقواعد البيانات.
* **المخرجات**: ملخص تعريفي شامل يوضح طبيعة المشروع دون تعديل حرف واحد في الكود.

#### 04. الفحص الفني الشامل — Project Health Check
* **الأمر السريع**: `/health-check`
* **كلمات التحفيز البديلة**: *"health check"*, *"audit codebase"*, *"فحص صحة المشروع"*
* **متى يُستخدم**: قبل البدء في إعادة هيكلة كبرى، أو عند استلام كود قديم (Legacy)، أو كفحص دوري لجودة المشروع.
* **الآلية الذكية**:
  - فحص الكود عبر 8 أبعاد: (1) المعمارية والأنماط، (2) معالجة الاستثناءات، (3) صحة الحزم، (4) جودة الكود، (5) الأمان، (6) الأداء، (7) الاختبارات، (8) إعدادات البيئة.
* **المخرجات**: تقرير منظم مرتب حسب الأولوية والخطورة من الحرجة (P0) إلى المنخفضة (P3)، مع روابط مباشرة للأسطر المتأثرة وخطوات معالجة محددة.

#### 05. مراجعة الكود البرمجي — Code Review
* **الأمر السريع**: `/code-review`
* **كلمات التحفيز البديلة**: *"review my code"*, *"review git diff"*, *"راجع الكود"*
* **متى يُستخدم**: قبل تقديم طلب دمج (Pull Request) أو بعد كتابة ميزة برمجية معقدة.
* **الآلية الذكية**:
  - فحص الفروقات البرمجية (Diff) المجهزة أو مقارنة الفرع مع الفرع الرئيسي.
  - التدقيق على: الأخطاء المنطقية، أمان القيم الفارغة (Null Safety)، حالات التزامن والسباق (Race Conditions)، تسريب الذاكرة، ومخالفات المعمارية.
* **المخرجات**: ملاحظات مراجعة عملية ذات أولوية، تحتوي على روابط للأسطر وحلول برمجية جاهزة للنسخ والاستبدال.

#### 06. إنشاء وتحديث التوثيق — Documentation
* **الأمر السريع**: `/documentation`
* **كلمات التحفيز البديلة**: *"update readme"*, *"document api"*, *"وثق المشروع"*
* **متى يُستخدم**: عند إنشاء أو تجديد ملفات الـ README، توثيق نقاط الـ API، شروحات المعمارية، أو سجلات القرارات المعمارية (ADR).
* **الآلية الذكية**:
  - يستخرج الحقائق والمعلومات حصراً من الكود الفعلي ونقاط التوجيه (Routes) والمتحكمات (Controllers).
  - يحافظ على التوثيق المفيد الموجود مسبقاً مع تحديث الجزئيات القديمة.
* **صمامات الأمان**: **منع التخيل والتأليف بشكل قاطع**؛ لا يتم توثيق أي نقطة نهاية أو إعداد غير موجود فعلياً في الكود.

### الفئة الثالثة (C): التطوير والتنفيذ البرمجي (Development & Implementation)

#### 07. بناء الميزات الجديدة — Feature Development
* **الأمر السريع**: `/feature-dev`
* **كلمات التحفيز البديلة**: *"build feature"*, *"implement new capability"*, *"ابن ميزة جديدة"*
* **متى يُستخدم**: عند الحاجة لتطوير وظيفة جديدة، شاشة مستخدم، أو منطق عمل في النظام.
* **الآلية الذكية**:
  1. دراسة الأنماط البرمجية الموجودة في المشروع ومحاكاتها بدقة.
  2. وضع خطة معمارية واضحة للطبقات (Data, Domain, Presentation).
  3. تغطية حالات الواجهة الأربع الأساسية: (التحميل Loading، النجاح Success، الفراغ Empty، والخطأ Error).
  4. كتابة اختبارات آلية للتحقق من عدم حدوث أي انتكاس في الكود القائم (Zero Regressions).
* **صمامات الأمان**: عدم إضافة حزم ومكتبات خارجية ضخمة أو فرض أطر عمل غير متوافقة دون مبرر.

#### 08. ربط الواجهات بالخوادم — API Integration
* **الأمر السريع**: `/api-integration`
* **كلمات التحفيز البديلة**: *"integrate API"*, *"connect backend endpoint"*, *"اربط نقطة الـ API"*
* **متى يُستخدم**: عند الحاجة لربط واجهات التطبيق أو الويب بنقاط نهاية REST أو GraphQL أو RPC.
* **الآلية الذكية**:
  1. تحويل نماذج الطلب والاستجابة إلى كائنات DTO محكمة ومكتوبة النوعية (Type-safe).
  2. استخدام عميل الـ HTTP المركزي في المشروع (مثل Dio، Axios، Fetch) والاستفادة من معترضات تجديد التوكن (Token Refresh Interceptors).
  3. معالجة حالات الترقيم (Pagination) ومختلف رموز الخطأ (401, 403, 404, 500).
  4. كتابة اختبارات وحدة مع محاكاة الاستجابات (Mocking).
* **صمامات الأمان**: الامتناع التام عن تخمين عناوين الـ API أو معاييرها دون عقد واضح وموثوق.

#### 09. إعادة هيكلة الكود — Refactoring
* **الأمر السريع**: `/refactor`
* **كلمات التحفيز البديلة**: *"refactor code"*, *"clean up this file"*, *"أعد هيكلة هذا الكود"*
* **متى يُستخدم**: لتبسيط الدوال المعقدة، إزالة التكرار، تفكيك الملفات الضخمة، أو تطبيق مبادئ Clean Code و SOLID.
* **الآلية الذكية**:
  1. تشغيل الاختبارات الحالية مسبقاً لضمان وجود أرضية تحقق ثابتة.
  2. تفكيك الكود المتشابك والتداخل العميق مع المحافظة التامة على الواجهات العامة (Public APIs).
  3. إعادة تشغيل الاختبارات بعد الانتهاء للتأكد من عدم تغير أي سلوك للمستخدم أو النظام.
* **صمامات الأمان**: حصر التعديلات بدقة في النطاق المطلوب فقط، ومنع تغيير السلوك الوظيفي الخارجي للكود.

#### 10. تدقيق الحزم والتبعيات — Dependency Audit
* **الأمر السريع**: `/dependency-audit`
* **كلمات التحفيز البديلة**: *"audit dependencies"*, *"check outdated packages"*, *"افحص الحزم والتبعيات"*
* **متى يُستخدم**: عند الاستعداد لترقية إطار العمل، أو البحث عن الثغرات الأمنية في المكتبات التابعة، أو تنظيف التبعيات غير المستخدمة.
* **الآلية الذكية**:
  1. تشغيل أوامر التدقيق الرسمية (`flutter pub outdated`, `npm audit`, `composer audit`).
  2. مقارنة المكتبات بقواعد بيانات الثغرات المعروفة (CVE).
  3. تصنيف التحديثات إلى تحديثات آمنة (Minor / Patch) وتحديثات كاسرة للتوافق (Major Breaking Changes).
* **صمامات الأمان**: **لا يتم رفع الإصدارات الرئيسية (Major) تلقائياً** لمنع كسر استقرار المشروع.

### الفئة الرابعة (D): الواجهات وتجربة المستخدم وضبط الجودة (UI/UX & Quality)

#### 11. تدقيق تجربة المستخدم — UX Audit
* **الأمر السريع**: `/ux-audit`
* **كلمات التحفيز البديلة**: *"ux audit"*, *"evaluate usability"*, *"فحص تجربة المستخدم"*
* **متى يُستخدم**: لتقييم سهولة الاستخدام، نقاط التعثر في التدفقات، أو مراحل تسجيل وتهيئة المستخدمين.
* **الآلية الذكية**:
  - قياس تدفقات المستخدم بناءً على معايير نيلسن الإرشادية (Nielsen Norman Heuristics) وإرشادات إمكانية الوصول (WCAG).
  - مراجعة العبء الذهني، منع الوقوع في الأخطاء، سهولة ملء الاستمارات، ووضوح الرسائل التوضيحية عند خلو البيانات.
* **صمامات الأمان**: الالتزام بالتحليل المنطقي والواقعي وعدم ابتكار أرقام أو بيانات أبحاث مستخدمين غير حقيقية.

#### 12. تدقيق الواجهات والتصميم — UI Audit
* **الأمر السريع**: `/ui-audit`
* **كلمات التحفيز البديلة**: *"ui audit"*, *"evaluate visual design"*, *"فحص التصميم والواجهة"*
* **متى يُستخدم**: للتأكد من الرقي البصري، محاذاة العناصر، درجات التباين، والالتزام بهوية التصميم.
* **الآلية الذكية**:
  - فحص التدرج البصري، أحجام الخطوط، وتناسق المسافات بشبكة 8pt.
  - فحص تباين الألوان وفق معيار WCAG AA (نسبة 4.5:1 على الأقل للنصوص).
  - مراجعة توافق المظهر مع الوضع الليلي والداكن (Light/Dark themes).
* **صمامات الأمان**: احترام هوية التطبيق القائمة وعدم اقتراح إعادة تصميم شاملة دون طلب صريح.

#### 13. نظام التصميم ومكتبة المكونات — Design System
* **الأمر السريع**: `/design-system`
* **كلمات التحفيز البديلة**: *"audit design system"*, *"catalog tokens"*, *"نظام التصميم"*
* **متى يُستخدم**: لبناء، تنظيم، أو صيانة مكتبة مكونات مشتركة ومحددات التصميم (Design Tokens).
* **الآلية الذكية**:
  - حصر وفهرسة محددات الألوان والخطوط والمسافات والظلال والحواف الدائرية.
  - كشف الانحرافات في التصميم (مثل الألوان المكتوبة كـ Hex مبعثر أو مقاسات خارج الشبكة المعتمدة).
  - توحيد المكونات المتطابقة أو المكررة في مكون واحد مرن يدعم المتغيرات (Variants).

#### 14. تدقيق التجاوب وتعدد الشاشات — Responsive Audit
* **الأمر السريع**: `/responsive-audit`
* **كلمات التحفيز البديلة**: *"audit responsiveness"*, *"check mobile layout"*, *"فحص التجاوب والشاشات"*
* **متى يُستخدم**: لاختبار تكيف التطبيق أو الموقع مع مختلف مقاسات الشاشات (الهواتف، الأجهزة اللوحية، الشاشات الكبيرة).
* **الآلية الذكية**:
  - محاكاة واختبار العرض عبر مصفوفة قياسات تبدأ من 320px حتى 1920px+.
  - رصد أي تجاوزات في التخطيط (مثل أخطاء `RenderFlex overflow` في Flutter أو أشرطة التمرير الأفقية غير المقصودة في الويب).
  - التحقق من ملاءمة أهداف اللمس (Touch Targets) بحيث لا تقل عن 48×48 بكسل/نقطة.

### الفئة الخامسة (E): الفحص، الأمان، والتسليم (Testing, Security & Delivery)

#### 15. مشغل الاختبارات الذكي — Test Runner
* **الأمر السريع**: `/test-runner`
* **كلمات التحفيز البديلة**: *"run tests"*, *"execute test suite"*, *"شغل الاختبارات"*
* **متى يُستخدم**: عند الرغبة في تشغيل الاختبارات الآلية وتشخيص أسباب الإخفاق.
* **الآلية الذكية**:
  1. التعرف التلقائي على أداة الاختبار المستخدمة (`flutter test`, Jest, Vitest, Pest, PHPUnit, Pytest).
  2. اختيار الاختبارات ذات الصلة بالملفات المعدلة لتوفير الوقت أو تشغيل الحزمة الكاملة.
  3. تحليل أسباب الفشل والتمييز بين الخلل البرمجي الحقيقي وبين المشاكل الناتجة عن إعدادات البيئة.
* **صمامات الأمان**: **يُمنع منعاً باتاً تعديل الاختبارات أو تعطيلها فقط لجعلها تنجح.**

#### 16. فحص ما قبل الإطلاق — Pre-Release Check
* **الأمر السريع**: `/pre-release-check`
* **كلمات التحفيز البديلة**: *"pre-release check"*, *"readiness check"*, *"فحص ما قبل الإصدار"*
* **متى يُستخدم**: قبل رفع التحديث إلى متجر التطبيقات (App Store / Google Play) أو إطلاقه لبيئة الإنتاج (Production).
* **الآلية الذكية**:
  - تدقيق صارم من 10 نقاط فحص تشمل:
    1. نظافة حالة Git وعدم وجود تغييرات غير ملتزم بها.
    2. خلو الكود تماماً من الأسرار والتوكنات المسربة.
    3. نجاح التحليل الساكن للكود (Static Analysis / Lint) بنسبة 100%.
    4. اجتياز جميع الاختبارات الآلية بنجاح.
    5. نجاح عملية البناء الخاصة بالإنتاج (Release Build).
    6. التأكد من ترقية رقم الإصدار ورمز البناء (Version/Build Number).
    7. التأكد من ربط نقاط نهاية الإنتاج بدلاً من خوادم التطوير.
    8. مراجعة صلاحيات النظام وأذونات الأجهزة (Permissions).
    9. التحقق من إعدادات تتبع الأخطاء وسجلات الانهيار (Crash Reporting).
    10. تحسين وتقليل حجم الحزمة النهائية (Minification / Tree-shaking).
* **صمامات الأمان**: تدقيق استشاري بحت؛ لا يقوم برفع الحزمة للمتاجر تلقائياً إلا بأمر المستخدم.

#### 17. استخراج ملاحظات الإصدار — Release Notes
* **الأمر السريع**: `/release-notes`
* **كلمات التحفيز البديلة**: *"generate release notes"*, *"write changelog"*, *"سجل التغييرات"*
* **متى يُستخدم**: عند تجهيز سجل التغييرات لصفحة GitHub Releases، أو شاشات "ما الجديد" في التطبيق، أو لمديري المنتجات.
* **الآلية الذكية**:
  - مقارنة وسوم (Tags) أو التزامات Git في الفترة المحددة.
  - تصنيف التغييرات بدقة إلى: ميزات جديدة (Features)، إصلاحات (Bug Fixes)، تحسينات (Improvements)، وتغييرات جذرية (Breaking Changes).
  - إنشاء مسودتين متكاملتين:
    1. **نسخة موجهة للمستخدم النهائي**: بأسلوب تسويقي واضح يبرز الفائدة المباشرة.
    2. **نسخة تقنية للمطورين**: تذكر تفاصيل الملفات والتحسينات المعمارية.
* **صمامات الأمان**: مستند بالكامل على سجلات Git الحقيقية دون أي اختلاق لميزات غير موجودة.

#### 18. التدقيق الأمني — Security Audit
* **الأمر السريع**: `/security-audit`
* **كلمات التحفيز البديلة**: *"security audit"*, *"audit vulnerabilities"*, *"فحص أمني"*
* **متى يُستخدم**: لتقييم الثغرات الأمنية في التطبيق، أو للتحقق من الامتثال لمعايير الأمان وحماية البيانات.
* **الآلية الذكية**:
  - تدقيق الكود وفق معايير **OWASP Top 10**:
    - الأسرار والمفاتيح المكتوبة نصاً داخل الكود.
    - إجراءات المصادقة وإدارة الجلسات وحماية التوكن.
    - الصلاحيات وحماية نقاط الوصول (IDOR).
    - حماية قواعد البيانات من الحقن (SQL/NoSQL/Command Injection).
    - ثغرات XSS و CSRF وسياسات CORS/CSP.
    - أمان التخزين المحلي في الأجهزة الذكية والمتصفح.
* **صمامات الأمان**: إخفاء وحجب جميع قيم الأسرار والمفاتيح الحقيقية في التقرير، وتجنب أي تعديل برمجي تلقائي بدون موافقة صريحة.

## 🛡️ المبادئ والمعايير الهندسية المشتركة (Global Standards)

تلتزم جميع مسارات العمل الـ 18 بمجموعة من الضوابط الأساسية الصارمة:

1. **الوعي الكامل بالمشروع (Project Awareness)**: فحص مسار العمل، قراءة ملفات التوصيف والإرشادات (`AGENTS.md`)، والالتزام بالأنماط المعمارية المتبعة في المشروع قبل اتخاذ أي إجراء.
2. **الجودة الهندسية العالية (Engineering Quality)**: كتابة كود نظيف، آمن نوعياً (Type-safe)، متوافق مع أحدث المعايير المستقرة، مع الفصل التام بين طبقات العرض، المنطق، والبيانات.
3. **أمان البيانات والأسرار (Safety & Secret Protection)**:
   - منع تضمين أو طباعة أي مفاتيح تشفير أو كلمات سر أو ملفات بيئة (`.env`).
   - منع الأوامر التدميرية التلقائية (`git reset --hard`, `git clean -fd`, `rm -rf`, force-push).
4. **دورة عمل محكمة (Structured Lifecycle)**:
   $$\text{سياق (Context)} \longrightarrow \text{فحص (Inspect)} \longrightarrow \text{تحليل (Analyze)} \longrightarrow \text{تخطيط (Plan)} \longrightarrow \text{تنفيذ (Execute)} \longrightarrow \text{تحقق (Verify)} \longrightarrow \text{تقرير (Report)}$$
